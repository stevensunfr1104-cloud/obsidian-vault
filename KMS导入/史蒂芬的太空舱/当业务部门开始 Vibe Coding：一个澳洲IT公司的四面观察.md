# 当业务部门开始 Vibe Coding：一个澳洲IT公司的四面观察

*原文：小红书 @进击的橘子猫（澳洲职场系列） | 整理：Steven*

这是一个发生在澳洲IT公司的真实故事。一个完全不懂代码的业务部门大佬，用一周时间"手搓"了一个CRM demo，却在公司掀起了轩然大波——C-level 高管为之振奋，IT部门如临大敌，PowerBI团队被告知"你们的工具已死"。四篇笔记，记录了一个组织在AI冲击下的阵痛与反思。
## 第一幕：导火索——一周手搓的CRM

故事的开端看似平常。

澳洲某IT公司，业务部门一位**完全不懂代码**的大佬，用 Vibe Coding 的方式，**一个星期**就做出了一个CRM Demo。界面看起来有模有样，各种功能点都有，演示效果流畅。

高层看完之后**大力赞赏**，随即宣布：

"这个可以取代我们的 Dynamics CRM 和 PowerBI。全IT部门要全力支持他上线。"

IT人的心，从这一天开始累了。
## 第二幕：风暴——IT圆桌会议的众生相

业务部门不懂code的大佬手搓了一个可以"取代"CRM和Power BI的demo后，**C-level 的上头真的上头了**，要求IT部门大力支持上线。

周五，IT部门紧急召开了圆桌会议。各方代表的表态，堪称一幅现代企业技术治理的浮世绘：
| 

| **角色** | **立场** | **核心观点** | 

| Cyber（安全团队） | 亮红灯 | 检测出了 **76个安全隐患** | 

| AI Architect（青年才俊） | 谨慎认可 | 东西挺好，但是上线需要**重头开始拆开做** | 

| Solution Architect（传统技术大佬） | 沉默反对 | 反对一切AI，此处省略一万字 | 

| CRM Platform Leader | 委婉拒绝 | "对不起这个code我不懂"——懂，但是支持不了一点儿 | 

| Data & Reporting Leader（作者经理） | 未表态 | 周一被约见CISO，讨论怎么support | 

会后，作者的感受是：**"technical这帮人大家都不傻，不想去擦屁股，可奈何上头压力大。"**
## 第三幕：天塌了——"Power BI is dead"

很多人问：高层们**明知风险**，为什么还想推动？

"一个非technical的人一周可以搓出来个CRM，里面各种function看着都有，那为啥还需要养着**几十人的Dynamics CRM和Power platform团队**，交着**百万的Microsoft subscription fee**呢？"

*——此招虽险，获益巨大。*

圆桌会议后，因为没有人明确表态支持，IT部门老大单独找作者经理谈话，言语间说**这个项目势在必行**，要他们组支持。

作者那"柔弱不能自理"的经理两眼一黑，说：**"我们的skillset在data和reporting这里，专业不对口呀。"**

老大回了一句：

"那你学呗，upskill你的team。"

最后，扎心的一句：

**"Power BI is dead."**

作者心情很低落。虽然大部分业务已经从传统BI转移到了digital/AI transformation project和Tech BA，但Power BI也是她热爱并钻研了近十年的工具，**"一下子悲凉的感觉。这时代的车轮还是滚滚的碾来了。"**
## 第四幕：反思——BI analyst 的十年领悟

面对"大老板说BI is dead，你怎么看？AI会不会取代BI？"这个问题，作者用了一个在行业里升级打怪了10年的视角，给出了她的回答。
### 误区：数据驱动决策？不，是人驱动决策

十几年前刚入行时，作者以为自己的工作流是：

*写复杂SQL —— 搭自动化pipeline —— 做炫酷dashboard —— 老板用数据拍板决策*

经过职场无数次鞭打才知道：

**"数据永远不会驱动决策，只有人会。而人，才是最复杂最不可控制的变量。"**
### 真相：技术只占30%，剩下70%全是软技能

一个合格的BIA（Business Intelligence Analyst），其实是 **BA + BI + DA** 的结合，甚至还要兼职背锅。漂亮的报表，只是最后交作业的那一刻。

**技术大概占30%，剩下70%，全是沟通、理解、对齐。**
### 一个真实的场景

当stakeholder轻描淡写说一句：**"我需要看一下gross profit的数据"**——恭喜你，命运的齿轮开始转动了。

这句话完全不是需求。接下来是一连串灵魂拷问：

- profit到底怎么定义？时间范围是什么？要达到什么目的？

- 哪些业务流程会影响这个数字？反过来，这个指标会影响谁？

- 不同团队对这个metric的理解一致吗？他们的老板点头了吗？

- 数据从哪里来，到哪里去？中间有没有被"污染"？

你还会发现一个很有趣也很崩溃的事实：**很多时候，业务自己都不知道自己要什么。**

于是你开始一层层拆流程，找数据源，对齐不同团队口径，跟平台、工程、产品来回沟通，顺便修几个历史遗留的坑。

最后你做出来的，仅仅是一个**所有人都接受认可的官方答案**。你的data可能不完美，但必须是经过反复验证、足够可靠、唯一且可落地的答案。
### 回答那个问题：AI会不会取代BI？

**"一定会取代那些只会做技术做报表的人，但很难取代那些能定义问题、推动决策、对齐认知的人。"**

作者自己做过的data agent POC，在精确调试（optimised for AI）后，产出和自动分析已经比她自己做的要快要好。但它有一个前提：

**"问题必须是清晰的。"**

而现实是，大部分时间，她的工作都是**试图在定义问题**。

## 对帆软客户的启示

这个故事虽然发生在澳洲，但对帆软的客户和国内数据从业者同样有警醒意义：

- **Demo 不等于 生产环境**：一个能跑通的demo和能支撑企业级业务的生产系统，中间隔着安全、性能、可维护性、数据治理等无数道鸿沟。

- **工具会变，能力不会**：PowerBI、FineBI、Tableau 都是工具，真正值钱的是理解业务、定义问题、推动决策的能力。

- **AI不会取代BI，但会重新定义BI**：未来的数据分析师，核心竞争力不再是"把报表做多好看"，而是"能不能帮业务想清楚问题"。

- **业务部门自服务是大趋势，但IT的治理角色不可替代**：低代码/无代码平台让业务能自己动手，但数据安全、口径统一、架构可持续性，仍然需要专业IT团队把关。

*"过去我们建数仓，是为了回答已知的问题。现在我们需要的，是一套AI能真正读懂的数据体系——以及一群能真正读懂业务的人。"*
