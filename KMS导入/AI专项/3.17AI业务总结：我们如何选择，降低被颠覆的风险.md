# 飞书文档的知识问答Agent玩完了

我玩了蛮久的openclaw。我用它做了好几个agent，最近做的agent是一个KMS的分析agent。

一年多以前，市面上最火的产品是什么？是知识库问答。飞书、阿里、企业微信都在做，但你看现在这个 OpenClaw 出来以后，包括我们团队自己做的corevo 搞完以后，**知识问答这类产品现在的形态已经基本上“死绝”了。**

# 现产品体系的规划重点思考

我在想，如果我作为飞书文档这个产品的产品经理，如果我来做飞书文档，在这种突如其来的巨变下，相比于做一些agent被 OpenClaw 这种产品形态做的知识库检索和总结的场景颠覆。

我应该做哪些事情，建立什么样的壁垒，才能在这种巨变之下，不被颠覆而是被加成。不管用户选择什么样的知识问答产品，我的知识库会被认为是更好用的企业级知识库？

我目前能想到的，其实就是知识库的可信知识图谱功能。具体来说，就是区分哪些是可信知识源，哪些是噪音知识源。

比如 OpenClaw 现在抓取的时候，如果有一个小可爱在自己的 KMS 里面写了一个财务报销规则，规定“公司所有人出行坐飞机头等舱，酒店必须五星级”，那 OpenClaw 抓取文档时一定会把它抓进去。那就有可能，当有一个人在问“我们公司的出差报销规则是什么”的时候，它会告诉这个员工：你出门就坐头等舱，你住酒店就住五星级酒店。

而一个知识库产品要作为 AI 的基建，一定要建立起自己的可信数据源。

如果这么去类比的话，这两天我经常被客户问到：
“你们公司的 BI 为什么不提供个人 Token？这样我就拥有了 BI 里我个人拥有的所有数据权限。我接一下 OpenClaw 去查数据、去问数，我人能查到什么，我的 OpenClaw 就能查到什么。那我为什么要用你们的 ChatBI？”

包括在一些语义澄清上，或者遇到有分歧指标的数据时，OpenClaw 这种产品未来可能也会做到跟我进行多轮对话，询问我到底要的是哪一个指标，以及不同的指标背后的含义是什么，可能会出什么问题。

客户是不懂的。“问知识”、“问文档”和“问数据”，这中间的产品复杂度目前还是有很大差距的。

目前，市面上绝大部分agent的架构设计，本质上都是在使用各种奇淫巧技绕过上下文窗口不够的问题。但是模型在发展，上下文窗口在可预见的未来仍然会不断扩张。

而 agent 架构也在飞速迭代，在发展各种 skills 和 tools，可以完成各种复杂任务的闭环和规划。

如果真的到了那一天，我不知道还要多久，可能还有很久，也可能不会太久。但是大概率会有。我们帆软整体（不单单是 AI 团队）的壁垒是什么？

在原产品体系中，**最重要的，需要加速发展的，就是“指标中心”以及指标中心建成所需要的数据治理体系。应该是非常重要一个点。**

基于 BI 的数据、FR 的数据等各种数据建立指标中心，构建公司统一的数据口径，从而减少 Agent的“幻觉”，不管这个Agent来自于哪里。——这就像是可信知识图谱之于飞书文档的意义。

应用复用也好，AI Native 的数据分析也好，想要交付好的效果。对指标中心的依赖都是极强的。而指标中心对于数据治理的依赖又是极强的。
# Agent产品如何避免上线即过时的厄运

在思考“随时被颠覆”的问题时，我也在不断的思考，我们在做AI native的产品时，在做Agent时也需要不断的思考，不断地拷问自己。

**我们做的生意和产品，究竟是会伴随着模型能力和agent架构的技术性突破的水涨船高，还是会被模型能力以及 Agent 创新型架构的突破所颠覆和变革？**

**这需要认真思考。不然很有可能面临辛辛苦苦搞一年，一夜回到解放前的悲剧。**

**以此为思考原点，思辨一下我们目前的三支明确承接了商业化目标的AI团队：Fineinsight、Clarai、Dora**
## Fineinsight

Fineinsight为什么是一个好的场景、好的产品概念（是不是好产品还有待验证），会随着模型能力和agent架构的技术性突破的水涨船高的产品

1、首先任何一个产品的立身之本，都是解决了企业的痛点。企业一直都有做洞察的需求，比如做战略洞察、舆情分析、区域空间分析、未来市场分析等等等。而要做这些分析，其实需要两个核心要素：

- 能够支撑分析的数据源：一个企业从哪里获取洞察所需要的数据呢？这些数据一直都是作为灰色资产在流通的，很多企业其实并没有门路得到这些数据。
- 基于数据源展开分析的思路：**解决了数据源的问题，企业拿到了数据源，进一步最缺的其实不是分析工具，数据分析从简单到复杂有太多选择了。而是分析思路。**比如面对 20GB的财务数据、税务数据、法律数据 ，我应该用什么样的分析思路，设置什么样的分析指标，才能得到一份分析结果。从这个结果中，洞察行业、场景和区域的空间、监控到某某行业的系统性风险、得到未来市场规模的推演？很多人其实并不知道该如何分析。而在这个痛点的催化下，诞生了全球的咨询顾问市场、行业分析报告市场，这些报告动辄上百万一份。

2、为什么Fineinsight的生意，是一个不错的生意呢，原因如下：

- Fineinsight本质上不是在卖一个工具：也不是在卖 Agent 的设计架构，也不是在卖平台的底座。
- Fineinsight卖的第一个价值是数据：我们战略合作采购了一批高门槛、高精度的数据。来自于xxx。
- Fineinsight买的第二个价值是专家经验的内化：帆查查将沈涛作为战略洞察专家的分析思路、洞察思路内化到了各种各样的 Agent 里面。让用户只需要提问，就可以更加低成本、便捷、专业的使用我们上一步提供的数据。
- 这种分析思路、分析方法和高门槛数据源本身是非常值钱的，至于具体的分析方式，未来可能会随技术变化，在人肉咨询顾问时代有咨询顾问手搓代码的分析方式，在 BI 时代有 BI 的分析方式，在 AI 1.0 时代有 AI 1.0 的分析方式，在 AI 2.0 时代也有 2.0 的分析方式。
- 而Fineinsight是会随着这些分析方式的迭代而变得越来越好用、越来越智能的，是随着技术的演进和变革水涨船高的。核心价值一直都在甚至被强化。
- 在官方agent之后，随着corevo能力的接入，这种数据被消费的门槛会进一步降低。

3、那这立马会来到下一个疑问，**如此一来，听起来我们的对手岂不是变成了德勤？我们要和德勤这类咨询公司正面硬刚吗？非也。**

- 我们在做的事情，是利用AI的技术变革，将战略洞察、市场洞察平权化，让战略洞察、市场洞察的门槛变低，让更多企业可以拥有。
- 就像简道云曾经做过的事情，**简道云并没有去硬刚任何老牌的业务系统，但是简道云通过零代码开发的方式，将企业拥有一个匹配自己需求的业务系统的门槛大大降低，获得了大批的增量客户。而非和传统业务系统厂商进行存量搏杀。**
- 但可能仍会被质疑，如此选择，我们是不是自降了客户level，那些头部客户不差钱，他们一定还会继续购买德勤的服务，而我们只能卖腰部客户。但我希望大家知道，这只是起点，而不是终点。就像简道云从小微客户起家，一路走来一样通过全民开发的理念占领了大量的头部企业，不乏上百万年费的客户。

4、需要警醒的是基于以上产品定位，fineinsight团队需要和营销线达成共识框定目标客群。切忌冒进，假如第一批客户直接瞄准帆软top100客户，大概率将铩羽而归

5、另一个在产品进展的问题上：FineInsight 里的“帆查查”还是查数，但到目前为止，我还是没有看到报告的出现。

**我们公司其实在 BI 上并没有做好这件事情。BI的数据大部分是客户自己的数据，不会找我们采购。而我们一直在卖给客户的是数据分析的工具，而不是分析思路，更不是分析结果。**

但是我们在补课，薛晨宇所带领的应用复用团队，努力想实现的就是卖BI的分析思路，乃至于买BI的分析结果。而未来应用复用的高价值产出，也一定会变成AI时代，独属于帆软的资产。
## Clarai

进一步盘点一下，Clarai这个产品团队其实护城河目前看有一个，就是在努力内化帆软作为TOB行业毋庸置疑的销售铁军的LTC。

将我们的帆软营销体系的客户跟进技巧、客户管理技巧等等各种经验与能力。变成线索评分/重点客户经营助手、客户洞察/访前助手、跟进记录助手、经营报告(销售周报、团队周报、老板每日早餐)助手等等。

直接帮助帮助企业更好的完成引流线索跟进商机成交的客户转化全流程。帮客户赚到更多钱，客户自然愿意给我们钱。

**但是不可否认的是，他不像Fineinsight一样，Fineinsight面向的是一个可被AI技术变革驱动产生增量需求增量客户可开拓下沉市场的机会。CRM过去是红海，AICRM也必将面临艰难的厮杀。**

但是目前的情况好过当年简道云做CRM的厮杀，**因为当年简道云做CRM是在没有任何外部变量的前提下，去追赶老牌厂商，去从他们嘴里抢蛋糕。**而当年唯一可打的卖点是我们的自定义程度更高。

但客户要CRM，核心诉求并不是自定义系统，让销售用CRM用的更舒服。**客户核心要的是一条铁律和真理，让销售能签更多单。**

但现在，在AI时代，几乎将所有CRM厂商拉到了同一个命题的同样的起点上：**有了AI的能力之后，一个真正能帮销售签单的CRM，而不是一个用来监视销售的CRM应该是什么样的？**作为CRM的半个门外汉，我们的历史思想包袱可能更轻一些，创新力更足。

我们有的资本是帆软营销铁军经验的抽象和内化，我们第一步拼的是我们产品的迭代速度，第二步拼的是市场占领的速度，第三步拼的是品牌心智的建立。**这是一条艰难的道路。**

目前这个团队是以和销售运营中心共创的形式打磨产品。团队内没有帆软的核心销售、和LTC的核心建设者参与。这会让这个团队走很多的弯路，又要从实践中吸取教训。这会浪费资源。这个问题要解决。

从我的视角看，帆软的销售体系非常牛逼，但是为了保证决策的严谨性，我还是希望多方验证一下：

- 帆软的销售体系牛逼到什么程度，这个牛逼是不是通用的，可迁移的？
- 帆软销售的牛逼，有多少比例是建立在组织和流程之上的？有多少是建立在师父教徒弟传帮带里面，还有多少比例是在不可明说的潜规则里的？

## Dora

目前看Dora的几个agent场景，金融营销活动推送agent、零售门店店长日推agent。通过AI总结客户的某张或者某几张数据看板，监控数据异常，并将总结和异常推送给客户。

他们的核心理念是相似的：

- 第一个是优化了用户使用数据的体验，从让用户找数据，变成了数据去找人。
- 第二个是降低了异常预警的配置门槛，看版的制作者不需要提前穷举所有的数据异常情况，然后基于数据预警配置固定的死的规则。只需要设置几个核心关键指标的预警，更多的数据异常预判可以交给AI来完成。
- 而这两个点的实现，是建立在帆软行业化、帆软历史沉淀的方案抽象能力之上的。我们让AI知道该如何总结某一行业某一场景的数据让结论更加的简洁但是高信息量。我们如何让AI知道该如何观测某一行业某一场景的数据让数据异常检测更加的灵敏且全面。

这几个场景务实，有客户愿意买单。

但是需要警惕：

- 他并没有创造非常高的增量价值。更像是BI体验升级的延长线。那在未来现BI产品、一体化数据分析的AI转型过程中，大概率会拓展相关能力，这个逻辑链路很通顺。**那把这个场景吃掉的可能不是外部竞争对手，而是我们自己的产品。**
- 谁来保证这些agent的质量，像Clarai一样，Clarai要联动更多的销售专家，LTC的专家。dora的专家团在哪里？如何发挥专家的价值，如何沉淀专家的能力。

另一块Dora切了一个企业内固定格式数据报告的场景。这种报告一般拥有极高的格式要求，与段落布局要求。整个报告的撰写过程一定程度上属于有严格精确验收标准的任务。自主规划式的agent过于灵活发散，难以稳定的保证交付结果。

而Dora通过硬编排的方式，将查询参数提取规则、数据源配置、组件取数规则、章节标题、章节大纲，固化下来。以保证agent交付的报告不管从内容上还是样式上都能符合客户的预期。这是一个被word报告充分验证过的市场。

但也有一些需要思考解决的事情：

- 能多大程度上向下兼容word报告：和word报告相比我们的报告产生方式更智能了，更灵活了。但是在格式上，能否完全向下兼容word报告的格式，乃至于其他能力。
- 能多大程度上弥补word报告的现存差距：历史上的word报告进入维护状态以后，仍有很多需求进来，这一次的推出，能解决多少需求？至少要做到心中有数。
- **dora团队对企业级agent交付结果的严谨性和客户的要求是有着最清醒和务实的认知。**在一段时间内（我无法预估长短）我认可这是该场景最好的实现方式。但仍需时刻关注最前沿的技术进展，这种方式很有可能是有生命周期的，那下一步呢？是继续寻找另一个无法被自主规划agent泛化覆盖的场景？还是拥抱自主规划式agent，还是其他更先进的agent架构。这是一个需要挂起思考提前思考的问题。但是又不能影响当前的做事节奏。

之前和horst聊天，经过上面的讨论，我有了更深的理解，我整理一下把对话内容贴出来：
### **最终企业场景的抽象聚类无非是：数据工程和算力工程以及组织流程**
#### 数据工程（结构化、半结构化、非结构化）

我们目前所有的解法都是帆软可操作边界内的数据工程构建：我们以业务流程项的沉淀数据和真实的结构化数据作为帆软可提供的可信数据源；

25 年那套指标中心加AI的东西的叙事，**对专业客户头部客户的吸引力是致命的**，因为这套东西本质上给客户会有一个很大的吸引概念，**就是我们看似好像把数据本体的问题也通过指标中心解决了。有很大的优化空间。**

在我们控制边界外的数据部分：飞书一定会做基于聊天、基于文档，偏业务SOP的业务半结构化可信数据源。

我们怎么样构建足够优秀的底座去承载它的取存管算用。向量库、图谱等等。没认知的客户最常提的一个问题就是，那我在IM上的聊天记录中间的业务知识你怎么获取？有认知的客户提的第二个问题就是，那我不同数据类型之间的多维关系你怎么管理？

业务知识对接这部分，我们确实没有飞书的整个能力底座，我们在这一块暂时都不知道对客怎么去讲故事

但最终会互相交叉互相引用，产生交集。

**这样一个平台一定会面对大厂的压力战。做吧就是硬刚，不做吧就是等死。操他妈的没有太好的解法。**

**有可能最终一个企业选择我们，还是选择飞书。可能就会变成是一个企业到底是以知识驱动为主、还是以数据驱动为主的两种策略。至于那些没有历史资产纯作平台的厂商，我觉得他们就是在瞎混。**

**而越早把这个东西推出，依托于帆软专注BI20年的品牌效应。越早建立客户心智与客户认知。**

**我们相比于飞书现在就是，这一块好像还真能从价值主张上打个1V1。**

**算力工程**

然后剩下的问题就是算力能力了。我们从数据出发，必然是不会绑定模型的，走的天然就是多模型混合的能力提升，对标GenSpark的逻辑。

而飞书基于知识出发，它必然是要绑定模型的。因为知识的数据体量会更大，它对模型的适配必须通过后训练、前训练，让模型本身去解析它的能力得到增强，而不只靠Agent架构和上下文的窗口。

怎么长期匹配多版本和水平的的混合算力能力。长期来看，我们要匹配的算力必然会是多能力版本的状态。一方面有边缘的小模型匹配，去低成本实现高频的业务操作。

另外一方面要匹配一些合规要求贼高的企业和行业，比如金融行业相关的。这种内部AI数据应用场景。（这一句没有达成共识，个人偏好，我不喜欢这些封闭的行业，但不会影响组织决策）

以上，目前有一种感觉就是AI项的能力我们补起来是很快的。

但是历史边界内的数据建模问题和历史没有的半结构数据的生态位问题，这2块涉及到数据的部分。

加上算力的能力的匹配度，是我们现在最痛苦的部分，也是短时间未展现，但长远必将形成威胁的点。

**虽然各路厂商在各自在自己的数据（结构化与非结构化）工程里，都没有真正解决图谱化的的符号主义的嵌合问题保障。但他们应该都在行动。**

## FDE

FDE目前风生水起，聊不完的线索、过不完的商机。进度可以说是非常顺利。

但是在我心里始终有一个达摩克利斯之剑。目前FDE并没有大规模进入交付阶段。

如何保证交付质量和交付后的项目运维，保证我们交付的FDE能够长期稳定的被客户使用。目前团队非常缺乏这方面的能力建设。

如果在这一关没有做好，FDE很有可能搬起石头砸了自己的脚。短期接住了客户、挣到了钱，但是从长期视角看。是会砸招牌的。

这一块应尽快和帆软项目团队形成联动，一方面通过项目组转型人员的扩充提升人才数量，缓解交付压力保证项目质量。另一方面直接沿用项目组的项目运维能力，保证已交付项目的长期稳定。

## 能力中台和创新业务平台

corevo

如果客户问，我帆软做的agent构建平台，有什么差异化的优势，飞书也会做这么一个平台，其他tob的厂商全都提供skills变为飞书的生态和基建。我为什么要买帆软的平台。

第一点，是agent的职业伦理的问题，如果飞书的agent调度帆软提供的skills和tools完成任务，任务完成稀烂的话，责任是谁的？是飞书用我工具的agent傻不会用我的工具？还是我的工具不好用？
所以产品之间协作，更合理的架构是A to A的架构，我承认飞书那里可能会有一个总控Agent分发企业内部的所有任务，但是这个任务是直接派发到对应的工具空间（如BI）的总控agent去完成的，对应工具空间的总控agent调用自己的skills和tools或subagent完成了任务后，将结果交付给飞书总控agent在交付给用户，这个链路中的责任定位是很清晰的。同时如果客户明确知道自己要的就是数据分析，他也可以直接来找我们的BI总控agent。

第二点，哪怕在不考虑职业伦理的情况下，
一个总控agent掌握1w个技能去调度100个产品所实现的效果；
和一个总控agent掌握部分skills对接多个数字空间的总控agent完成任务的效果。
一定是第二种的效果更好（我目前的认知是这么认为的，但是我还要再找多个专家进一步学习求证）

第三点，目前所有的 OpenClaw 类产品还都是 C 端的，这些 Agent 运行在用户的个人电脑上，或者是个体用户的一个独立空间里。

而我们做的这个 Corevo，它是运行在企业服务器上的；
1.openclaw这种产品更像是个人助理，它是每个人都要部署一套的；而 Corevo 是一次部署、全员使用的。

2.所有员工和 这个产品 的交互都是留痕存档的，管理员可见，日志可溯源的。不像用其他产品，企业里的数据动了，你却不知道是谁通过什么 Agent 动了企业里的东西。

这次没有写能力中台。不是因为不关心不思考这块业务。

是因为这个团队做的事情，不在这个命题之下。

我希望这个作为内部的创新者和技术先锋，走在最前面，尽可能的往前多探一段路。

能让帆软的所有团队提前感知到新的技术变革和新的产品设计理念。为我们的行动争取一些提前量。哪怕可能只有一个月半个月。

当然我每过一段时间会盯一下前一段时间研究的转化。
