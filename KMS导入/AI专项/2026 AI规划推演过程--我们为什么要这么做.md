# 一、 通用 ChatBI复盘

基于对当前技术边界和客户落地的复盘，我们识别出通用 ChatBI 无法逾越的三个核心雷区，它们构成了准确率的“天花板”：

- 
**意图识别模糊：** 在通用场景下，业务“黑话”多义且晦涩。没有垂直场景的上下文约束，大模型无法精准理解“销量”在不同部门的定义差异。

例子： “我看下昨天的量。” 在电商场景是 GMV，在运维场景是日志吞吐量，在销售场景可能是线索数。通用大模型没有上下文，只能瞎猜。

- 
**工具能力匮乏：** 简单的 Text-to-SQL 无法处理复杂的企业级计算（如复杂的同环比、留存分析），而Text-to-DSL 又将产品的能力局限于 BI 产品之内。AI 缺乏像人类专家那样拆解问题、使用多种工具的能力。

- 
**数据基建垃圾：** “Garbage In, Garbage Out”。客户的数据口径不统一、元数据缺失。如果不解决底层数据治理，上层的 AI 永远不可能算准。

很多企业在上 ChatBI 之前，连基本的数仓分层、指标字典都没有建设好。如果“毛利”这个词在财务报表和销售报表中计算逻辑不一致，AI 无论多聪明都会答错。

**结论：** 在短期（1-2 年内）试图做一个“全能 ChatBI”是徒劳的。未来的胜出者，属于那些**收敛场景、解耦工具、控制数据范围**的垂直领域 Agent。在有了充足的积累之后再向通用进发。

# 二、 战略转向：打造垂直领域爆款 Agent

我们的新方向是：**从“做更好的 ChatBI 工具”，转向“制造特定岗位的数字员工”，即垂直 Agent。**

我们不再追求“回答所有问题”，而是构建**垂直 Agent**（如市场洞察 Agent、销售主管早餐播客 Agent、零售管家 Agent、 舆情风险监控Agent）。

以市场洞察为例：

- 
**限定洞察场景：** 提前穷举场景内的黑话，明确服务边界，对用户意图多轮澄清，拒绝回答界外问题。把行业分析师的思维模型（SWOT、PEST、波特五力等变体）编码到 Agent 的推理链中。

- 
**限定市场洞察需要的数据范围：**核心依赖外部规整数据源，摆脱企业内部数据源千企千面的数据治理难题，将数据治理难度从“全域治理”降低为“局部清洗”。

- 
**能力闭环：** 不止于查数、看数，具备真正的行动力，生成报告、触发预警、定时推送等等。

以销售主管早餐播客 Agent为例：只是举例，该理念是数据找人，场景可以泛化，集运的码头集装箱运转效率早报也是一样的。

# 三、 垂直 Agent的中局混乱之解：Agent平台暗线
## 问题分析

如果在 26 年 H1 我们跑出了第一个爆款 Agent，那么我们需要考虑几个问题：

- 对团队来说，冷启动的边际成本递增：限定场景解决了可用性不足的困境，这在单场景下是对的。但在多场景下可能由于规模效应导致成本激增。
垂直场景的专业性意味着每个 Agent 都需要深度调优（ agent 框架选择、微调、Prompt 工程、知识库建设）。
- 如果每个新 Agent 的上线都需要产品经理和开发投入巨大的精力去构造新的 tools（预警、报告、websearch），那团队会陷入重复造轮子的资源浪费。
- 每个agent 的账户体系、权限体系、消息体系、日志体系、数据接入层都单独建设。

- 对最终使用者来说，入口分散且混乱，语义不统一：
构造了多个垂直 Agent（如：市场洞察 Agent、零售管家 Agent、 舆情风险监控Agent），用户面对的就不再是一个入口。
用户有一个问题，不知道该问哪个 Agent，或者一个问题涉及多个 Agent。这种“碎片化”会抵消垂直场景带来的准确率提升。

- 不同的 Agent 如果各自为政，可能会出现指标幻觉。
e.g.市场 Agent 从外部抓取的数据算出的“市场份额”，如果和 FineBI 内部数据算出的“销售表现”在对齐时出现了口径冲突（比如对“季度”的定义不同），用户会立即丧失对整个系统的信任。

- 垂直 Agent 能表现好的原因是限定数据范围，但这也会带来新的问题。
多个 agent，单独接入客户数据系统业务系统，只针对自己需要的几张表做数据治理，那帆软会有多个 agent 团队，分别去和客户的信息化部门做对接，每次都要重复上一个 agent 团队的实施过程。

## 解题思路

- 第一个 Agent 完成10 个交付时，立即停下来进行架构盘点。把这个 Agent 里通用的鉴权模块、日志模块、Tool 调用模块剥离出来，作为“平台 V0.1”版本
- 同时配合的最前沿的研究，优化 agent 架构，并不断迭代。
- 基于“平台 V0.1”的其他 Agent，验证平台和 agent 架构的普适性，然后正式推广。 【2026 年可能就到此为止了，第一阶段关键控制点用好我们已经铺设在客户那里的数据基建，是别的公司没有的】
- 一个总控/路由 Agent它的职责不是分析数据，而是理解意图并分发给对应的垂直 Agent，最后还要负责将多个 Agent 的结果进行逻辑汇总。
- 建立一个统一的语义中台。所有 Agent 无论多垂直，涉及核心业务逻辑时必须调用统一的逻辑接口，而不是让每个 Agent 的 Prompt 里各自写一套计算逻辑。
- **沉淀用户和 agent 交互的过程资产，更加了解用户的的特征和诉求，进一步驱动 agent 的更优表现。【中期的关键控制点，长坡厚雪，累加效应】**
- 在平台之上，构建 Agent 市场，客户可以根据自己的需求，在平台上增购多个 Agent，解决自己的业务难题。**【长期的关键控制点，生态和方案效应】**
- Agent 生产工厂的底座：把agent 构建、工具挂载、数据治理等相对标准化、工具化提炼总结最优解，让垂直 agent 团队能够足够小，足够敏捷，专注于表现提升。甚至有一天，可以让非技术背景的行业专家能快速配置出一个新的垂直 Agent。（不抱什么希望）

注：此平台绝非类似 coze、dify 等 agent 搭建平台。他核心专注于让 agent 表现更好的一个平台。
# 四、美好愿景和残酷现实之间的鸿沟之解：FDE 特种兵和数字人才

如果以上计划都能够顺利推进。

我们将能够实现中描绘的美好愿景：**未来帆软会转型成为一家人工智能公司，向客户提供基于一体化平台的解决方案和数字员工（Agent）。**

但我们短期还面临一个巨大的考验，即留给我们的时间窗口。

**相比于25年突然席卷的AI场景化浪潮，大量企业在25年还是观望和学习。**

**经过25年的市场教育，客户逐渐冷静，并且开始聚焦于AI真的能落地的场景，同时已经有大量客户在26年的信息化预算中，做了AI场景化的预算。**

但我们知道，目前的AI产品有一个死穴：**越通用，越没用**。 所以我们的AI产品，必须必须聚焦、必须垂直，才能真正的解决客户问题、创造价值、商业变现。

但这会撞上未来2-3年的一个主要矛盾： 历史上我们是通用工具厂商，我们的客户五花八门，客户的业务千奇百怪。**我们短时间能提供的标准品很窄 vs 客户想要的东西范围很广。**

**我们的标杆客户等不及，我们的销售也等不起，我们公司也无法承担标杆客户流失**

**如果标杆客户的心智变为“帆软是一家传统的BI公司，帆软公司做不了AI”，将会深刻影响帆软未来的发展空间。**

为了解决这个问题：

- 我们会组建一支FDE特种兵团队。这支团队将成为帆软在AI时代搏击浪潮的尖刀，是为我们争取时间窗口的最关键的特种部队。标准化、工程化、规模化的产品建设需要时间，需要试错。但是和客户贴身肉搏，精准的实现单个客户的诉求这是我们的强项，也是我们必须守住的阵地。详见及其子页面
- 同时我们也会打通FDE**和数字人才的联动逻辑。****通过FDE**把AI培训盘活，通过AI培训为FDE及标准Agent做好客户教育。
培训现场就是最好的需求挖掘场：培训脑暴场景 -> 现场用平台搭MVP（最小可行性产品） -> 筛选出有价值的大需求 -> 呼唤 FDE 团队进场做深度实施。
- FDE如果遇到客户需求不明确，只是想要AI，但不知道怎么用AI，不知道用AI可以解决企业里的哪些问题，可以呼唤数字人才团队，为客户赋能，挖掘出企业内部的需求场景，并且教育客户AI能力边界，找到真正适合AI落地的场景。

# 六、现产品体系的 AI 话：走出办公室，进入客户现场是第一要义

上面讲的内容都是一个 AI native 的下一代数据分析产品应该怎么做。这是一条风险极高的路线。

但**现产品体系仍是帆软未来几年最大的现金流，最重要的产品线**。如何保证现产品能够加成 AI 功能，在原来的市场中能够立于领先之地，是一个非常重要的课题。

如果客户对于 AI 诉求偏保守，在采购 BI，**我们如何能够告诉客户我们的 BI 相比于其他的 BI 更加的智能。这是未来几年要回答的，非常重要的问题。**

在 2025 年，因为整体产研变革的节奏问题。对这部分的投入不大。

同时一体化平台的本身构建不完善。AI在老产品上做？没资源。AI在新产品上做？新产品本身还不稳定。

**同时在 2025 年我们也没有收到客户提出的 AI 需求， 所以 2025 年并没有很高的优先级。**

**不过现在我们知道了，**** AI 的需求客户是不会主动提出来的，大概率也是提不出来的，因为大部分客户也不懂AI 能帮他做什么。**

应用搭建团队是有一些探索落地，并且拿到了一些经验的。应用搭建 25 年上线了 10+ AI 能力加成。有些做的很不错，但有些做的不完善。

从这些不完善的功能里我们更加加深了对一句话的理解：**产品经理必须走出办公室，进入客户现场，才能真正的做出好的 AI 功能。**

比如以 AI 辅助搭建表单的功能为例：

没有任何用户提过这个功能。但我们认为 AI 可以提高表单的制作效率。于是第一版我们做了一个功能，输入一句话“我需要做一个客户跟进表单”，系统会自动完成表单的搭建。

但这个功能在一些复杂场景下表现不佳，因为同样是客户跟进表单，不同客户需要的表单是不一样的。

做这个功能的产品同学，在帮客户做系统的时候，识别到了一个场景。就是客户的出库单，是有标准的线下纸质文档的。如果在没有 AI 的时候客户会拿着这张纸质出库单，在简道云上一个字段一个字段拖出来。

但是有了 AI 之后，我们完全可以做到，让客户拍一张照，AI 自动识别并理解单据含义之后，精准搭建出来一张线上表单。这个功能现在已经在开发的过程中了。

**客户的需求不会发生变化，AI 只是改变了需求的实现方式。但同时大多数人还没有意识到，实现需求的方式已经可以进入下一代了。**

以前在产品初期，我们定性的感知到产品有很多体验不足的地方，比如操作繁琐、点击步骤多、功能路径不清晰等等。但是这些体验不足的地方客户也不爱提。“又不是不能用”

但是我们想要做一款，让用户体验很好的产品。于是，我们搞体验式客户拜访，产品经理+交互，在客户公司集中办公一周，观察那些使用帆软产品的用户是如何使用的，然后总结用户使用过程中的体验卡点，变成设计开发任务去改进。

在AI 时代，为了敏锐的感知到AI 可以改变哪些需求实现的方式。我们要重新做一遍这件事情。

所有帆软产品经理都需要

- 学习 AI 的原理，弄清楚 AI 的能力边界。
- 然后主动出击，在客户现场观察、上手直接操作，感受完成的客户使用产品的流程，然后识别、总结、提炼，哪些环节引入 AI，构造什么样的功能，可以帮助客户大大的提效。

每一条产品线和模块，都会制定使用AI 提升客户体验的产品规划。
