# 应用背景

Polars是帆软自研的高性能计算引擎，旨在为公司的BI服务（目前包括九数云和BI）提供高性能计算能力。为了支撑业务侧的计算性能需求，Polars实现了近SOTA的计算能力，这也极大的增加了Polars引擎的复杂度，加之Polars的文档建设不甚完善，以及Polars作为数据处理系统本身极高的领域复杂度，对于新人来说上手存在困难。

本人尝试利用AI工具，对Polars进行研读，以加快对Polars系统设计和实现的理解，加深对相关数据处理领域知识体系的理解与学习，并加速部分较低工作规模需求任务的完成。

# 使用场景以及效果
## 快速入门

- 
/init 请您我创建一份该项目的基本架构文档，要求给出该项目的核心功能以及该功能的大致设计和实现，并基于模块构成以及模块之间的依赖关系，给出起模块之间的互操作关系。您需要返回使用简体中文学术语言编写的文档。

注意/init对于现成文档的关注度要高于代码或项目结构，因此注意清除过期文档。

## 接口和简单模块的重构

- 
“我现在有这样一些类，XX4JNI类的实现依赖于XX类，这使得XX4JNI会加载XX类的一些非必要逻辑导致可能的传递依赖问题，现在我希望将这样被XX4JNI类和XX类同时依赖的逻辑抽取出来独立为XXUtils类，由XX4JNI类和XX类同时依赖于XXUtils类。请您识别本项目中符合该特征的这些类，然后执行相应的重构。”

- 
需要相对较好的模型，较好的模型对于源代码的模式识别能力比较好，可以实现更优秀的重构

## Code Analyze

- 
“某某逻辑是怎么实现的？”

- 
在直接/init的基础上配上CC和Codex足够强大的检索Agent可以基本满足规模相对小且相对复杂的逻辑的精确分析，对模型能力有较高的需求（使用的4.5-sonnet，4-sonnet表现就不稳定不少）

- 
基本上，对于开发较为规范的项目，在分析具体模块上不会出现比较严重的幻觉、理解偏差以及上下文差异，因为逻辑上讲，良好设计的模块本身可以在较小的外部依赖的情况下解释清楚他的编码视角的输入输出、执行逻辑以及执行目的，AI读不清楚通常说明模块过于巨大或者内聚性不够耦合性太强，该场景比起改进Agent不如改进代码

根据Agent有所不同：CC和CodeX通常有从文件中提取出方法体的能力，Gemini和Qwen目前还需要全文分析（以@为例，Gemini和Qwen会对你的输入照单全收，而CC和Codex通常只会表现出偏重。）

# 个人心得
## 与AI Coding IDE之间的差异

- 
上下文构建逻辑差异

- 
上下文分析策略差异

AI Coding IDE 通常会对WorkSpace构建Embedding数据，主要用于加速补全，必要的时候会用作内建的语义搜索索引（Github Copilot的做法），并利用索引化的搜索结果去降低上下文长度。

- 
AI Cli Agent通常先将用户的原始需求经LLM拆解成步骤，各个步骤再调用Agent以获取对应的上下文，利用Agent返回的结果拼接成大的Context得到最终请求LLM的内容。

- 
Cli Agent则基于本地工具构建上下文，必要时会对上下文进行压缩，但在中短长度对话通常不会压缩，保持原文传输。

- 
AIcoding IDE通常有着更高的Token利用效率，并且相比于步骤拆分细碎的Cli Agent来说有更快的响应能力；CLI Agent则基于未压缩文本以及相对宽松的上下文策略有更高的语义细节优势，相应的其推理结果更加完全、降低幻觉的可能性。

通常而言，事实上体验越先进的Cli Agent，其构建LLM上下文的策略会越保守，上下文信息提供的会相对更多，消耗token的速度会更快。

- 
Agent使用差异

CLI通常有更激进的Agent使用策略搭配相对保守的推理策略，其形成“分析问题的问题域以及关联方 -> Step by Step 式的调用Agent来搜集能支撑问题处理的关键上下文 -> 将收集到的关键上下文用于实际处理问题 -> 验证问题是否正确处理”的分析流程，其中Step by Step的操作较为复杂和多步骤，且写执行权限要的相对更多。

- 
AI Coding IDE遵循着类似的工作流，但其对于Agent的调用通常并不Step by Step而更倾向于一次获取必要的信息（比如对于一个Todo-list上的一次任务，只生成一次文本），以及对于生成结果的dump与后续验证，相对更为简单直接。

- 
这个更多是设计差异而非能力差异——AI Cooding IDE也可以引入大量的Agent并提供激进的调度策略，但主流的AI Coding IDE 没有这么干。

## 模型和Agent的关系

个人认为：Agent决定功能边界和能力边界，以及体验的上限；模型决定能力的下限。

- 
LLM的不确定性设计下决定了其要处理复杂问题通常需要大量的良好定义的约束和引导以有效的提供推理依赖上下文并约束推理边界，这些需要Agent提供。

- 
在Agent提供良好的约束和引导的情况下下，需要LLM输出足够可靠的结果，从而确保Agent后续步骤的可靠性。

实际使用下，仅就Code Review 而言，各家模型的水平大差不差（CC GPT Gemini Qwen），但Agent以及客户端的质量差别很大，对使用体验影响很大。

- 
典型1：对于“请您基于递归分析调用链的分析情况，分析一下XX类的具体操作和实现逻辑”这样的需求，CodeX和CC往往可以实现“递归检索”，能把调用链作为上下文传给LLM；Gemini和Qwen则通常只能分析一层调用；//todo 插张图

- 
典型2：在对系统缺乏了解的情况下，询问“某某方法是怎么实现的”，CodeX和Claude Code的实现通常是“搜索文件名 -> 根据搜索到的文件去搜索文件内容”，Gemini（Qwen）更倾向于“直接搜索文件内容，并返回匹配的关键字的大段上下文”，相对而言前者的实现范围配合其比较保守的Agent重试策略更为精确，后者对于欠规范的查询或者项目表现不佳，且可能引入过多无关数据导致理解偏差。

目前主流的模型和Agent均强耦合，未来如果出现了近SOTA的开源Agent可以考虑研究一下模型对于问题处理的影响情况。（感觉不乐观，现在开源SOTA的Coding IDE 和cursor相比都是纯纯的原始人状态，gemini-cli和cc比也差异巨大）
# 现状与未来？
## 上下文长度问题

目前的主流模型均无法突破100W Token上下文窗口的限制，且通常在同一时空背景下的不同模型、模型推理泛化能力越强，上下文窗口相对越小，整体体现出“在保持可处理窗口大致不变的情况下、提高推理能力”的特征，反映了模型在处理大规模文本上的困境现状。此外，随着上下文长度增长，即使是SOTA的模型也会在长对话或者大上下文的情况下，处理最近会话的时候产生关注点偏移。
## Prompt Engineering

- 
随着Ai Coding Agent的能力发展，以及模型能力的强化（尤其是其在有限上下文的自我约束、避免过于泛化的能力），PE的侧重点逐渐发生变化：从“用自然语言一步步教AI做事”，逐渐变成了“对神灯许下足够清晰和明确的愿望”。

- 
需要从“提供无歧义的流程”进化到“提供无歧义的需求”
